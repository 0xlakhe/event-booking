# EventBook technical design

## Status and scope

Read `REQUIREMENTS.md` for acceptance criteria and `Intern_Project_Brief.pdf` for the authoritative assignment. The user has selected **FastAPI and Docker Compose for local development**; Next.js + TypeScript and deployed Supabase PostgreSQL remain required. Compose is a PDF bonus and a selected user requirement here. All detailed choices below are **proposals selected for implementation**, not requirements quoted from the brief. ## Architecture and module interfaces

Browser → Next.js frontend → FastAPI REST API → PostgreSQL (local Compose or hosted Supabase). In this diagram the frontend's browser code calls FastAPI directly; Next.js hosts the interface, not a backend proxy.

- **Frontend module:** pages, forms, loading/error/empty states, auth state, and a typed HTTP client. Its only data interface is FastAPI. No Supabase SDK, database credentials, Next.js API routes, or backend server actions.
- **Auth module:** register, login, resolve current user, logout. Hides hashing, sessions, and credential lookup behind a small interface; callers receive an authenticated user, never a password hash or session hash.
- **Events module:** public listing/detail and admin event mutations/attendees. Owns filtering, capacities, and event editing/deletion policy.
- **Bookings module:** book, list own bookings, cancel. Its interface accepts the authenticated actor and identifiers; it owns ownership checks and the whole transaction, rather than requiring route handlers to coordinate locks.
- **Database module:** one SQLAlchemy engine and request-scoped sessions using synchronous SQLAlchemy + psycopg, with Alembic for versioned migrations. Use synchronous FastAPI handlers for blocking database work. Share transaction helpers without adding a generic repository framework or hypothetical adapters.

Use a simple `frontend/` and `backend/` repository split. Backend modules can be ordinary Python files/packages with Pydantic input/output models. Dependency injection provides database sessions and current-user resolution. HTTP handlers translate results/errors; transactions remain local to the owning module. Tests exercise the HTTP interface against PostgreSQL, including real commits for concurrency tests.

## Proposed database model

Use a private `eventbook` schema outside Supabase's exposed Data API schemas. UUID primary keys are generated by the backend; timestamps are timezone-aware PostgreSQL `timestamptz`. Unless stated nullable, columns are NOT NULL. All creation timestamps default to database time. Use text plus CHECK constraints for the two roles rather than adding an enum migration workflow.

| Table | Columns and constraints |
| --- | --- |
| `users` | `id uuid` PK; `email text` unique, stored trimmed and lowercase, CHECK nonempty and equal to normalized form; `password_hash text`; `role text` default `user`, CHECK in (`user`, `admin`); `created_at timestamptz`. |
| `sessions` | `id uuid` PK; `user_id uuid` FK to users ON DELETE CASCADE; `token_hash text` unique; `created_at timestamptz`; `expires_at timestamptz`, CHECK greater than creation. Store only SHA-256 digest of the high-entropy bearer token. |
| `events` | `id uuid` PK; `title text`; `description text`; `starts_at timestamptz`; `venue text`; `total_seats integer` CHECK > 0; `created_at timestamptz`; `updated_at timestamptz`. CHECK trimmed title, description, and venue are nonempty. |
| `bookings` | `id uuid` PK; `user_id uuid` FK to users ON DELETE RESTRICT; `event_id uuid` FK to events ON DELETE CASCADE; `created_at timestamptz`; nullable legacy `cancelled_at timestamptz`, CHECK null or >= creation. |

Relations: one user has many sessions and bookings; one event has many bookings. New cancellations delete the booking row; the nullable `cancelled_at` column remains only for compatibility with pre-existing soft-cancelled rows. Those legacy rows are excluded from seat counts, own-booking results, and new cancellation actions; this release does not clean them up.

Indexes beyond PK/unique indexes:

- Partial UNIQUE `(user_id, event_id) WHERE cancelled_at IS NULL` prevents duplicate current bookings while allowing legacy soft-cancelled rows to coexist.
- Full `(user_id, created_at, id)` on bookings supports own-bookings queries and the user FK.
- Full `(event_id)` on bookings supports the event FK and cascades; a small dataset does not need another active-event index initially.
- `(starts_at, id)` on events supports upcoming listing order.
- `(user_id)` on sessions supports its FK and session lookup by user.

Compute `seats_left = total_seats - COUNT(active bookings)`; do not persist a separate seat counter. A CHECK constraint cannot express this cross-table invariant: capacity relies on the shared event-lock transaction protocol and exclusive backend write access described below. Do not conceal a negative result with clamping; treat it as an invariant failure.

Use parameterized SQL/SQLAlchemy expressions everywhere. For listings, aggregate active counts for the selected page in a query rather than issuing one query per event. A simple title substring scan is appropriate at this scale; no search extension is proposed.

### Database access and privileges

Use a dedicated non-owner runtime database login with schema USAGE and only the table privileges needed by the API. Use a separate migration/seed credential for schema changes and admin seeding. Restrict runtime user creation to allowed columns so inserts receive the database `user` role default; grant no runtime UPDATE privilege on `users.role` and omit role from public input schemas.

Registration inserts must omit `role` rather than explicitly setting even `user`: model it as a database server default, so column-level INSERT restrictions work with the ORM. Keep SELECT rights limited to what internal auth queries need and serialize only public fields.

Grant no `eventbook` access to PUBLIC, Supabase `anon`, or Supabase `authenticated`; check default privileges on future tables as well. Keep the schema outside the configured Data API exposure list. This design uses custom auth and backend authorization, not `auth.uid()` or Supabase Auth policies. Private-schema isolation and grants are the access control strategy; adding custom per-user RLS context is unnecessary for this small backend-only design. Verify isolation directly with unprivileged credentials.

The runtime credential writes bookings and events and deletes bookings; all app, seed, and maintenance writes must honor the transaction protocol. It has no UPDATE privilege on the legacy `cancelled_at` column. Cross-table capacity is not protected against arbitrary privileged SQL. Keep administrative SQL out of normal application flows and preserve the invariant in fixtures/seeds.

## Custom authentication

Propose opaque, revocable sessions instead of JWTs to make logout immediate without refresh-token machinery.

1. Registration accepts `email` and `password` only. Normalize email; validate its shape and maximum 254 characters. Password length 8–128 characters; do not trim or silently truncate it. Reject extra input fields including `role`. Insert a normal user and return its public fields; the frontend then directs the user to login.
2. Hash passwords with Argon2id using a maintained library's recommended configuration. Never store/log plaintext passwords. On login, use a generic `INVALID_CREDENTIALS` error for unknown email and wrong password; perform a dummy hash verification for unknown users.
3. On successful login, create a cryptographically random 32-byte URL-safe token, store its SHA-256 hash, and return the raw token once. Expire the session after 24 hours, with no sliding expiry or refresh endpoint. Multiple sessions are permitted.
4. Send it as `Authorization: Bearer <token>`. Resolve the hash to a nonexpired session joined to the current database user; role comes from that user, never request input. Missing, revoked, or expired sessions return 401.
5. Logout deletes the matching session. The frontend clears its token even if the logout request fails; if the server is unreachable, explain that server revocation did not complete. A request already authenticated before logout may finish.

Frontend storage proposal: keep the token in `sessionStorage` for this small app, restore it on client hydration, then verify through `/auth/me`. Clear it on 401 and successful/logout attempt. This survives refreshes within a tab without cross-site cookie deployment requirements. Trade-off: JavaScript-readable storage exposes the token to XSS; render event content as plain text, avoid unsafe HTML, and never log tokens. Closing a tab usually ends local persistence but is not server revocation. Use HTTPS in production. No auth tokens in URLs or server-rendered HTML. Login rate limiting remains an optional bonus.

Frontend session races (user-selected robustness): the auth provider tags each login, logout, and expiry with a monotonic operation generation. A delayed `me` restoration or a logout whose revocation resolves after another login must not overwrite the newer account or clear its stored token; only the still-current operation may change local session state. A successful current login also finalizes authentication readiness itself, so a still-pending restoration for an older session cannot leave the app stuck on its loading state. Authenticated page actions also capture the token that started them and re-check it after every await, so a booking or recovery response belonging to a replaced session cannot update the new session or force it to expire. A recovery 401 expires the initiating session only while that session is still current.

## REST contract

Base prefix: `/api`. JSON uses snake_case; UUIDs are strings; timestamps are RFC 3339 UTC strings with `Z`. All authenticated routes require the bearer token. Booking, history, and cancellation serve normal users only: admins receive 403 there (management-only scope) and manage events instead. No endpoint accepts a caller-selected booking owner.

Public shapes:

- `User`: `id`, `email`, `role`.
- `EventSummary`: `id`, `title`, `starts_at`, `venue`, `total_seats`, `seats_left`.
- `EventDetail`: summary fields plus `description`.
- `Booking`: `id`, `event` (EventSummary), `created_at`. No other user's identity or cancellation-history flag in own-booking responses.
- `Attendee`: `booking_id`, `user` (`id`, `email`), `booked_at`; active bookings only.
- Collection envelope: `{ "items": [...], "page": 1, "page_size": 10, "total": 12 }`.

| Method and path | Permission | Request and success response |
| --- | --- | --- |
| `POST /api/auth/register` | Public | `{email, password}` → 201 User. Duplicate email → 409. |
| `POST /api/auth/login` | Public | `{email, password}` → 200 `{access_token, token_type: "bearer", expires_at, user}`. |
| `GET /api/auth/me` | Authenticated | 200 User. |
| `POST /api/auth/logout` | Authenticated | No body → 204. Already-invalid token → 401; frontend still clears local state. |
| `GET /api/events` | Public | `q`, `page`, `page_size` → 200 paginated EventSummary; upcoming only. |
| `GET /api/events/{event_id}` | Public | 200 EventDetail; past-event detail remains accessible. |
| `GET /api/bookings/me` | Authenticated non-admin (admins 403) | `page`, `page_size` → 200 paginated current bookings, including past; legacy soft-cancelled rows are excluded. |
| `POST /api/events/{event_id}/bookings` | Authenticated non-admin (admins 403) | No body → 201 Booking. One seat; actor comes from session. |
| `DELETE /api/bookings/{booking_id}` | Owner, non-admin (admins 403) | No body → 204 after hard-deleting the owned future booking; a repeat returns 404. |
| `GET /api/admin/events` | Admin | `q`, `time_filter` (`upcoming` default, `past`, `all`), `page`, `page_size` → 200 paginated EventDetail, including descriptions. Public lists remain EventSummary. |
| `POST /api/admin/events` | Admin | Full event input → 201 EventDetail. |
| `PATCH /api/admin/events/{event_id}` | Admin | Nonempty subset of event input → 200 EventDetail. |
| `DELETE /api/admin/events/{event_id}` | Admin | No body → 204 if deletion policy permits. |
| `GET /api/admin/events/{event_id}/attendees` | Admin | `page`, `page_size` → 200 paginated Attendees. |

Event input: `title` (trimmed, 1–200 characters), `description` (trimmed, 1–5000), `starts_at` (explicit offset required), `venue` (trimmed, 1–300), `total_seats` (strict integer, 1–100000). These bounds are proposed validation choices. Reject nulls and unknown fields. Allow admin creation of past events (edits and deletion of started events are rejected as read-only history); booking eligibility uses their current start time. No publication/draft state is needed; created events are published immediately.

All collection routes paginate in SQL with LIMIT/OFFSET. Default page 1 and size 10; bounds page >= 1, size 1–50. Out-of-range pages return an empty `items`, not an error. Trim `q`, maximum 200 characters; empty means no filter. Search is case-insensitive literal title substring: escape `%`, `_`, and the escape character before LIKE binding. Public listing uses `starts_at > database_now`. The admin listing adds a `time_filter`: `upcoming` (`starts_at > now()`) is the default, `past` uses `starts_at <= now()`, and `all` combines both. That condition filters `total` and the page items alike, before pagination. Event ordering is upcoming `starts_at ASC, id ASC` (nearest first), past `starts_at DESC, id DESC` (most recent first), and `all` lists the upcoming block first followed by the past block; own bookings use `created_at DESC, id DESC`; attendees use `created_at ASC, id ASC`. `total` counts the same filters. Offset pagination may shift between requests as data changes, acceptable here; use one short read-only REPEATABLE READ transaction for count and items within a response.

### Error convention

Use `{ "error": { "code": "EVENT_FULL", "message": "This event is full.", "fields": {} } }`. `fields` is optional and maps input field names to readable validation messages. Normalize FastAPI validation failures into this envelope; never serialize submitted passwords or tokens in validation details.

| Status | Meaning / codes |
| --- | --- |
| 401 | `AUTH_REQUIRED`, `INVALID_SESSION`, `INVALID_CREDENTIALS`; include appropriate bearer challenge. |
| 403 | `ADMIN_REQUIRED` (admin-only routes), `ADMIN_BOOKING_FORBIDDEN` (admins on user-booking routes). |
| 404 | `NOT_FOUND` for missing event/booking; use the same response for another user's booking to avoid disclosing it. |
| 409 | `EMAIL_EXISTS`, `ALREADY_BOOKED`, `EVENT_FULL`, `EVENT_STARTED`, `CAPACITY_BELOW_BOOKINGS`, `EVENT_HAS_BOOKINGS`. |
| 422 | `VALIDATION_ERROR`, including invalid UUID/query/body input. |
| 503 | `TEMPORARILY_UNAVAILABLE` for database connectivity or lock timeout; rollback first. |
| 500 | `INTERNAL_ERROR` with generic message; details only in sanitized backend logs. |

Map expected unique/FK conflicts by known constraint name after rollback; unknown database errors are not exposed. Do not automatically retry booking POSTs after transport failure; refetch own bookings and event availability before presenting the next action.

## Booking transactions and concurrent writes

Use PostgreSQL **READ COMMITTED** for writes. Every booking, cancellation, event edit, and deletion locks the same event row with `SELECT ... FOR UPDATE` before checking related state or changing anything. Locks are database locks, not in-process mutexes. Keep transactions short; no password hashing or network work while holding event locks. One event per mutation; if future work touches several, lock in UUID order.

Finish authentication's read transaction before starting the module-owned transaction. Retain plain actor ID/role values rather than an expired ORM object that triggers an unexpected query. Choose isolation before any statement in each transaction; collection REPEATABLE READ must not be applied after an authentication query has already opened a READ COMMITTED transaction.

**Book:** authenticate; begin; lock event or return 404; in a subsequent statement obtain `clock_timestamp()` and reject `starts_at <= current time`; check duplicate active booking; count active bookings in a separate statement after acquiring the lock; reject when count >= capacity; insert; commit; return 201. The unique partial index remains the duplicate guard. Return success only after commit.

**Cancel:** authenticate; look up the booking scoped to the actor to obtain event ID without locking the booking; begin a READ COMMITTED transaction; lock the event first; reread booking and ownership; evaluate the event time with fresh database wall-clock time. Reject started events without mutation. For a future active booking, delete the row and commit before returning 204. A missing booking, a repeated cancellation after deletion, or a legacy soft-cancelled row returns the same 404; legacy rows are not deleted by this path. Never lock booking first and event second.

**Edit:** admin check; lock event; reject with `EVENT_STARTED` when the event has already started (fresh wall-clock time after the lock), preserving started events as read-only history; count active bookings after lock; reject proposed total below the count; update validated fields and `updated_at`; commit. Changing a future event to a past time makes subsequent booking/cancellation fail; disclose this behavior in README and use clear UI feedback.

**Delete:** admin check; lock event; reject with `EVENT_STARTED` when the event has already started, so historical data is never deleted or rewritten; reject with `EVENT_HAS_BOOKINGS` if any current booking exists. Otherwise delete the event and cascade any legacy soft-cancelled rows; commit. This intentionally preserves events with active attendees and avoids silently cancelling them. Do not add force-delete or admin cancellation features.

**Why last-seat races are safe:** writer A locks the event; writer B waits. A counts, inserts, and commits. B then obtains the event lock; its subsequent count statement sees A's committed booking under READ COMMITTED and rejects the full event. Capacity edits, cancellations, and deletion serialize on that same row. Avoid combining the pre-wait count into the locking statement/CTE, where a stale statement snapshot would defeat this protocol. A rolled-back writer consumes no seat. Fresh time after lock waits avoids admitting requests based on request-arrival time. Eligibility is judged at the locked check, not the instant a response reaches the browser.

Configure a finite lock/statement timeout (propose 5/10 seconds per write transaction); roll back and return a clear retryable 503 on timeout. A success response whose delivery fails may still have committed; own bookings resolves that ambiguity.

Never-overbook is mandatory. The brief lists the dedicated simultaneous-last-seat handling/explanation as a bonus; this proposal chooses the safe protocol as its ordinary capacity implementation, with the explicit concurrent test/explanation as bonus evidence. Docker Compose is selected required local tooling; login rate limiting remains deferred optional work.

## Time and frontend behavior

The user-selected visual system uses cream/off-white surfaces and charcoal text,
with thin borders and shared spacing across public, auth, booking, and admin
pages. CSS tokens live in `frontend/src/app/globals.css`: paper `#f7f5ef`,
surface `#fdfcf8`, ink `#292923`, muted text `#69685f`, borders `#d9d6cc`, and
secondary surfaces `#eeece4`. Georgia headings and the locally available Avenir
Next/Segoe UI sans-serif stack require no downloaded fonts or new dependencies.
The homepage's short introduction links to the event list on the same page;
event cards use two desktop columns and one phone column, with explicit date,
venue, availability, and one View event action. The brand links home for visitors
and normal users, and to management for admins. Visitor navigation includes Log
in and Sign up; existing user/admin navigation and route guards remain intact.
Forms, feedback, and pagination share the same controls, with visible keyboard
focus, a skip link, reduced-motion support, and responsive stacking. This is a
presentation follow-up to TASK-008; REST, session, and database contracts do not
change.

Collection refreshes retain results only while their owning context is unchanged:
public events use query/page, event detail uses route ID, own bookings use
account/page, and admin events use account/query/time filter/page. Matching
background refreshes expose a compact accessible updating status and mark the
collection busy; event availability is labeled as updating rather than presented
as current. Initial loads and context changes use the stable loading state and
must not display rows, counts, or pagination from another context. Account
changes/logout must never expose previous private rows. A failed refresh may
retain matching rows alongside retryable error feedback; request/session guards,
existing action guards, and backend-authoritative availability remain unchanged.
The event detail's initial request and Suspense fallback share a stable,
layout-matching skeleton for the back link, heading, description, facts, and
booking panel. A screen-reader-only status announces the load; skeleton shapes
are decorative and hidden from assistive technology, and no actions are
rendered until the current event is available.

To reduce common-navigation latency without an unbounded data layer, list
event links prefetch public detail only on hover, keyboard focus, or touch
intent. Public detail responses are deduplicated and held in a memory-only LRU
cache (20 entries, 30-second expiry) with at most three concurrent intent
prefetches. A completed fresh cache hit is immediately ready and makes no
second detail request; an unfinished prefetch is not a cache hit. Expired or
invalidated entries are fetched before booking is enabled. Booking,
cancellation, admin edit, and deletion invalidate the affected detail entry.
The cache contains no session or booking-ownership data.

The public event list also uses a memory-only LRU cache keyed by exact search
query and page (eight entries, 30-second expiry). Fresh hits are immediately
ready without revalidation; expired or invalidated entries are not shown as
fresh. The one short-lived list-origin snapshot is the same cache entry, not a
second copy, and remains pinned while its origin is active. A confirmed booking
corrects the booked event's row in every cached list that shows it (one fewer
seat, never below zero) without extending that row's freshness window, so the
returning list stays instant with truthful availability. Rejected or uncertain
booking outcomes, cancellation, and admin event creation/edit/deletion clear
public list entries. The backend remains authoritative for capacity and
mutation decisions.

The bookings page uses a separate memory-only LRU cache (eight entries,
30-second expiry) keyed by an ephemeral identity for the current authenticated
session and page. A bounded 32-entry per-session event-membership cache with the
same TTL lets a fresh detail route show the booked marker without scanning
history. Positive membership also populates from cached own-bookings pages; a
complete history scan may cache either outcome. Logout, session expiry, and
every successful login/session restoration clear private caches synchronously.
Booking/cancellation invalidate the active session's private entries, and
revision checks prevent older in-flight responses from repopulating them.
Tokens are never cached. These caches do not replace backend authorization or
mutation checks.

When opening detail from the public list, keep one short-lived same-tab origin
containing only the list URL, event ID, scroll position, and bounded public
page snapshot. Accept only a same-origin public-list path. “Back to events”
uses browser history only for a matching list origin and otherwise falls back
to `/`; browser Back/Forward retains the normal history URL. On matching
return, reuse the exact list cache entry only while fresh, then restore scroll
in a layout-phase effect after the rows are committed and layout is forced. If
the entry expired or was invalidated, fetch without showing stale rows and
restore the matching origin's scroll after the new rows arrive. Origin metadata
has a separate short lifetime and never re-inserts an expired or invalidated
snapshot. If the origin expires or no longer matches, do not restore its scroll.
Consume the exact origin after restoring so a later same-URL visit cannot replay
rows or override intentional scrolling. A failed fetch does not present stale
availability as current. Do not globally suppress route scrolling.

When a visitor activates a public-list event link with an ordinary same-tab
click, keep the list rendered while the public detail request resolves. Show a
small accessible opening status on that link, suppress duplicate activation of
the same navigation, and only capture the list origin and navigate after the
request succeeds. A failed request leaves a visible retry action on the list;
a changed query/page or unmount makes its response inert. Modified clicks,
downloads, and non-self targets retain native anchor behavior. A ready bounded
public-detail cache entry may navigate immediately; the detail route renders
that completed fresh entry ready on its initial render and makes no second
detail request. Direct cold detail URLs retain the ordinary loading skeleton
and retryable error state. Expired/invalidated detail entries are fetched before
booking is enabled.

Store and compare instants in UTC. The event becomes ineligible when `starts_at <= database clock`. Reject timezone-naive API input. For the small app, present all dates and the admin form in **Nepal time**, visibly labeled `Asia/Kathmandu (UTC+05:45)`; convert the admin's local form value to an explicit `+05:45` timestamp before sending. Avoid interpreting `datetime-local` using the evaluator's device timezone. Return UTC, format explicitly in Nepal time, and use backend responses as the final authority.

Proposed pages: upcoming events `/`, detail `/events/[id]`, `/register`, `/login`, `/bookings`, and `/admin` with event forms and attendee display. A simple responsive layout and small reusable forms suffice. Include all states required in `REQUIREMENTS.md`. Preserve search/page in URL parameters, reset page when search changes, and discard stale search responses. Route guards improve UX; backend permission checks remain decisive. Admins land on `/admin` after login, see no public Events navigation, and are redirected from public list/detail pages to management only after session restoration confirms their role. Upcoming and started admin cards show descriptions inline, with a three-line preview and accessible Read more/Read less controls only when the text overflows. Descriptions arrive in the paginated admin collection query, not per-card requests. Metadata appears once; there is no separate Details action or started-event notice. The admin list adds an Upcoming/Past/All time filter (Upcoming default) whose selection lives in a `time_filter` URL parameter so refresh and browser navigation preserve it; changing filters keeps the title search and resets to page one. Attendees stay reachable, and started events have no edit/delete controls; backend conflict messages still explain rejected mutations. The admin page carries no public-browsing link (no Back to events), since administration is a management-only flow; Logout comes from the shared navigation, and logging out from an admin route (`/admin` or `/admin/*`) returns the visitor to the public list `/` rather than leaving them on the admin "log in as an admin" prompt. Local state clears even when revocation fails, and the revocation warning stays visible on the destination page because it lives in shared auth state. These presentation choices are user-selected, not PDF mandates.

On booking/cancellation/edit, disable duplicate submission while pending and refetch affected availability/bookings after success or capacity conflict. Do not optimistically claim a seat before commit. Own-booking pages show current bookings only; cancellation removes the row from history after refetch, with no cancelled-status item. Disable ineligible actions with an explanation. The frontend gates booking and cancellation on the event start time (`starts_at <= now`), updating on a lightweight interval so eligibility changes while the page stays open without a reload; the backend clock remains authoritative and still rejects started-event mutations. After a booking response is lost, the client never auto-retries: it scans the actor's entire booking history (there is no narrower per-event lookup endpoint) before reporting a definite absence, and reports an uncertain outcome when that verification itself fails. The detail page reuses a fresh session-scoped membership result or scans history on load — for signed-in users only — to derive the action label: a current booking for the event yields a disabled Booked, which outranks full and started labels and suppresses the started note. Scans are guarded by generation, session token/identity, and cache revision so stale responses cannot repopulate invalidated state. Failures leave the action available, with an ALREADY_BOOKED response as the repair path. A scan 401 is deliberately not an app-wide session-expiry trigger; the next authenticated action remains responsible for that. Authenticated responses use `Cache-Control: no-store`; avoid static caching of availability and private data. Clear private frontend state when auth changes.

## Seeds and tests

Propose repeatable seed execution with fixed UUIDs, admin/user emails and passwords supplied through seed environment variables. Hash credentials through the auth module; seed privileged role assignment uses the seed credential only. Never reset existing passwords or delete non-seed data on ordinary reruns. Create missing seed records in a transaction; document that a populated dataset is not silently reset.

Create 12 future events and one past event, using times relative to initial seeding so default page size 10 exercises pagination. Include a future event of capacity 2 with one real active booking by the seeded normal user, leaving one seat free for demonstration. Existing seed timestamps remain stable on rerun; if they become stale, explicitly refresh the dedicated demo dataset before submission rather than rewriting live customer data. Logins in README are demo credentials, not infrastructure secrets. Verify seeds live before sharing.

Use pytest and FastAPI TestClient against an isolated PostgreSQL test database/schema, never production. Apply the same migrations; isolate ordinary cases and explicitly clean committed fixtures for concurrent tests. SQLite cannot validate these locks/index semantics. A single documented test command must run the required suite with its configuration documented.

Proposed meaningful tests (the brief requires at least three; these are selected coverage, not additional source requirements):

1. Book → duplicate rejected → hard-delete cancellation → availability restored → rebook succeeds.
2. Full and past events reject booking; past cancellation rejects without mutation.
3. Another user cannot cancel a booking; unauthenticated/private calls fail; normal users cannot use any admin route.
4. Reducing capacity below active count fails and leaves the event unchanged; equal count succeeds.
5. Deletion rejects active bookings and permits deletion when only legacy soft-cancelled rows remain, with the expected legacy-history cascade.
6. Register cannot set role; password stored hashed; login, expiry, and logout invalidation work; private response fields never leak hashes.
7. Search/pagination execute database filtering, stable ordering and correct totals; literal wildcard input is handled.
8. Bonus evidence: two independent committed database connections book one remaining seat concurrently; exactly one succeeds, the other gets full, final active count equals capacity. Also exercise a capacity edit racing a booking if time permits.

Use past/future offsets with generous margins for ordinary tests. Make the clock check explicit and test the equality rule at the backend helper seam without introducing production clock overrides. Test the database access grants and absence of exposed schema access. Finish with the live checklist in `REQUIREMENTS.md`, including direct API calls.

| `tools` | One-off backend-image service under profile `tools`, with no published ports. Runs bootstrap, migrations, seeds, and tests explicitly; privileged/test configuration is supplied here rather than to normal app services. Wait for healthy `db`. |

Networking and configuration:

- Browser opens `http://localhost:3000`; `NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api`. The browser cannot resolve Compose names `backend` or `db`; never give it a container-only API hostname.
- Backend connects to `db:5432`, database `eventbook_dev`, with the restricted role. `localhost` inside that container is not PostgreSQL. Container checks may call `http://backend:8000/health`; no Next.js proxy is needed.
- Local CORS allows `http://localhost:3000`. Local DB traffic uses the private Compose network without TLS; hosted Supabase DB traffic requires TLS. Use the same schema, migrations, constraints, and application grants in both environments.
- Commit a root `.env.example` with local-only placeholders for bootstrap, runtime, migration, test, and seed-account credentials. Copy to ignored `.env`. Map variables explicitly per service: frontend gets only its public API URL, backend only runtime configuration, tools gets bootstrap/migration/test/seed configuration. Never pass the whole environment file into frontend or reuse hosted credentials locally. Keep any per-app examples consistent with these defaults.

Implement `/health` as readiness: 200 only when runtime DB access and the expected schema/migration revision are ready, otherwise sanitized 503. Use it for backend health; use an HTTP readiness check for frontend. Health checks perform no migrations. A fresh database stays unready until explicit setup completes, hence the startup order above. Compose dependency checks cover initial startup only; backend must recover connections after DB restarts.

`postgres_data` preserves development and test databases across restarts. Bootstrap gives the development runtime no test access and test runtime/migration roles no development access; revoke default PUBLIC CONNECT and grant database access explicitly. Test setup verifies exact `eventbook_test` name and expected test credentials before migration/cleanup, then cleans only test fixtures/schema. Test execution uses runtime permissions, not the test schema owner. Do not run parallel suites sharing this schema; concurrent cases use independent connections and clean committed fixtures.

Document `docker compose down --volumes` separately as a deliberate **destructive local reset** removing database and frontend dependency/cache volumes, followed by full setup again. It is never normal startup or test behavior. Database initialization hooks run only on empty data volumes; keep repeatable role/database provisioning in explicit bootstrap rather than assuming hooks run on restarts.

Local plain PostgreSQL preserves transaction/index semantics without unused Auth, Studio, or storage services. Supabase-managed roles and Data API isolation must additionally be checked on the hosted project; local PostgreSQL cannot prove platform configuration. Bootstrap must apply grants only to existing platform roles, with hosted-specific checks performed during release verification. Production remains Supabase PostgreSQL with the frontend and backend deployed as two Vercel Services in one project (see Configuration and deployment design); Compose does not replace compulsory public deployment.

## Configuration and deployment design

Chosen hosts (user-authorized 2026-10-17): one Vercel project with two Services — nextjs `frontend/` and fastapi `backend/` (entrypoint `app.main:app`) — plus Supabase PostgreSQL. `vercel.json` leaves both services private and exposes only `/api/*` and `/health` to the backend, everything else to the frontend; a service rewrite forwards the original path, so the browser calls FastAPI directly on the same origin (`NEXT_PUBLIC_API_BASE_URL=/api`), preserving the required direct browser-to-API HTTPS path without CORS or a Next.js proxy. These are replaceable hosting choices, not brief mandates.

| Location | Configuration |
| --- | --- |
| Frontend | Serves only `NEXT_PUBLIC_API_BASE_URL` to the browser (`/api` on Vercel: same-origin through the services rewrite); only `NEXT_PUBLIC_*` values are inlined into the bundle. Vercel scopes variables to the project, so backend values exist in the frontend service's environment too; no frontend code reads them. |
| Backend | Secret `DATABASE_URL` for limited runtime role; `ALLOWED_ORIGINS` exact frontend/local origins; timeout/pool configuration. |
| Migration/seed environment | Privileged `MIGRATION_DATABASE_URL`, seed account inputs; unavailable to browser/runtime where possible. |
| Test environment | Isolated runtime `TEST_DATABASE_URL` and tools-only `TEST_MIGRATION_DATABASE_URL`; explicit test guard against production/development targets. |

Use a small bounded SQLAlchemy pool (propose size 5, no overflow, one initial backend worker), connection health checks, TLS database connections, and the Supabase **session-mode pooler** when a direct endpoint is unsuitable for hosting connectivity. Keep total connections within the project's limit. Avoid transaction-pooler/driver prepared-statement mismatches by choosing session mode for this small backend. Keep each mutation on one checked-out connection for its full transaction. Run migrations once as an explicit release action, not from every application worker. On Vercel, keep `DB_POOL_SIZE` small (for example 2) because Fluid compute multiplies warm-instance pools against the shared Supabase pooler.

Allow only known origins in CORS, with Authorization and Content-Type headers and the required methods/OPTIONS. No authentication cookies or credentialed CORS are needed for bearer auth. CORS is not authorization. Keep development origins separate from production values. `/health` follows the readiness contract above without exposing configuration; verify hosted database grants and platform isolation separately during release checks.

Commit `.env.example` placeholders for each app and ignore actual env files. Sanitize logs; never publish runtime/seed secrets.
